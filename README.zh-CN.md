# Render Stats Scanner

*[English](README.md)*

一个 Unity 编辑器窗口：游玩时持续盯着 Stats 面板，渲染出问题的那一刻自动截图。
退出 Play 模式后给你一份独立的 HTML 报告，每张截图都配着**那一帧**的完整渲染统计
——于是你能看见 batches 飙起来时屏幕上到底在画什么，而不是对着一个已经滚过去的
数字猜。

菜单：**Tools → Render Stats Scanner**

## 为什么还要再造一个

Stats 面板只告诉你当前帧，Profiler 什么都有但得自己去翻。两者都不直接回答真机卡顿
时你真正想问的那个问题：*batch 数翻了三倍的时候，在画什么？*

相比手动盯 Stats 面板，这个工具多做了三件事：

- **按基线判突增，而不只是固定阈值。** 固定的「batches > 150」规则，对一个平时就
  160 的场景毫无意义，对一个平时 30 的场景又抓不住问题。这里用最近 60 帧的**滚动
  中位数**当基线，当前帧超过基线若干倍才触发，因此同一套设置在主菜单、玩法、弹窗
  之间都能用。绝对阈值仍然保留作兜底。
- **退出 Play 模式不丢数据。** 事件在发生的瞬间就 flush 到磁盘，所以退出时那次会
  清空全部内存字段的 domain reload，不会把你这轮采样一起带走。停止游玩，报告就在
  那儿了。
- **记录整帧，而不只是触发的那个数。** 每次抓拍存 17 项，其中包括 draw call 在
  **动态合批 / 静态合批 / GPU Instancing** 三路上的拆分——这才是真正能告诉你「是
  合批崩了，还是单纯多了几何体」的依据。

## 环境要求

| | |
|---|---|
| Unity | 2022.3（验证过的版本；没有用到更新的 API，更早的 LTS 大概率也能跑） |
| 依赖包 | 无 |
| 平台 | 仅编辑器——它读的是 `UnityEditor.UnityStats`，和 Stats 面板同源，永远不会被编进 player |

## 安装

### 通过 UPM

Window → Package Manager → **+** → *Add package from git URL*：

```
https://github.com/plgamer/unity-render-stats-scanner.git
```

### 手动

把 `Editor/` 拷进工程里任意一个 `Editor` 目录下。

## 用法

1. 点 **Play**。
2. 打开窗口，点 **Start Scan**。
3. 正常游玩。窗口显示实时统计，抓拍自动发生。
4. **退出 Play 模式。** 报告自动生成并载回窗口。（**Stop Scan** 效果相同，但不退出
   Play 模式。）

产物落在 `Logs/RenderStatsScanner/session_<时间戳>/`——在 `Assets/` 之外，Unity
不会导入它，而标准 Unity 工程的 `.gitignore` 里 `Logs/` 本来就被忽略：

| 文件 | |
|---|---|
| `report.html` | 自包含报告。截图走相对路径，整个 session 目录可以直接打包发给别人 |
| `events.tsv` | 每次抓拍一行，25 列。也是窗口回读的数据源 |
| `summary.tsv` | 均值、峰值，以及当时生效的阈值 |
| `shots/` | PNG 截图 |

窗口里有历史会话下拉，不离开编辑器就能对比优化前后两轮。

## 判定参数

| 参数 | 默认值 | |
|---|---|---|
| 突增检测 | 开 | `batches ≥ 中位数 × 倍率` **且** `batches − 中位数 ≥ 最小增量` 时触发。两个条件都要满足，所以平时 5 batches 的场景不会在 8 的时候报警 |
| 倍率 | 1.5× | 超过滚动中位数多少倍算突增 |
| 最小增量 | 30 | 绝对增量下限，压掉轻量场景上的噪声 |
| 绝对阈值 | 150 / 80 / 200 / 20 万 / 20 万 | batches、SetPass calls、draw calls、三角形、顶点的兜底线 |
| 截图冷却 | 1.0 秒 | 一次突增通常会持续很多帧，靠它避免单个事件把磁盘塞满 |

基线取**中位数**而非均值，正是为了让被测量的那些尖峰帧不会反过来把基线抬上去。
突增检测需要攒够 60 帧才会启用；绝对阈值从第一帧就生效。

参数保存在 `EditorPrefs` 里。

## 已知限制

- `ScreenCapture.CaptureScreenshot` 是异步的。图片会比与之配对的统计数据晚一两帧落
  盘，所以在画面变化很快的场景里，截图可能比数字描述的内容稍晚一点。报告生成被刻
  意延迟了 1.5 秒，等最后几个文件写完。
- 采样由 `EditorApplication.update` 驱动，每个编辑器帧一次。如果编辑器降频（窗口在
  后台、domain 暂停），采到的帧数会少于游戏实际渲染的帧数。报告里的耗时是墙钟时
  间，不能替代 Profiler。
- 设计上就只在编辑器里跑。它量的是编辑器的渲染，**不等于**真机的渲染——用它定位问
  题，然后到真机上验证修复效果。
